=== int8 vs int4 sensitivity on REAL Kimi K3 weights ===
captured: 2026-07-30T17:04:50Z
method  : 31 attention-projection tensors sampled from the released checkpoint by
          HTTP range read - real weights, no full download. 384 rows per tensor.
          Each tensor is round-tripped through int8 and int4 with one fp32 scale per
          32 elements, and the mean relative reconstruction error is recorded.

WHY THIS EXISTS
  This is the measurement behind the engine's central design decision: the resident
  trunk is STREAMED VERBATIM rather than quantised.

  Quantising the trunk is the obvious way to fit a 113 GB resident set into less RAM,
  and it is the wrong one. K3's technical report section 4.1.4 states that the experts
  are MXFP4 with quantisation-aware training "while all non-expert components remain
  in higher precision" - that list IS the trunk, so it was never trained to tolerate
  4-bit. This study checks whether that holds on the actual weights.

  It does. So the engine quantises NOTHING: routed experts are already MXFP4 in the
  checkpoint and are multiplied in that form, and the trunk is copied byte for byte.
  Streaming costs zero reconstruction error, which is why memory could be made a dial
  without any accuracy claim attached to it.

=== what this says ===
int8 costs about 1% mean relative error on these weights; int4 costs about 17%.
That ~18x gap is consistent across every tensor sampled, and it holds equally in
KDA-layer and MLA-layer projections -- there is no layer type that tolerates int4
noticeably better.

This is why the engine does not quantise the trunk at all. Even int8 - the far better
of the two - trades a measurable error for memory the streaming design recovers for
free, and int4 on the trunk is not defensible at 17% mean weight error. Only the routed
experts are 4-bit, and only because the checkpoint already ships them that way, trained
for it.

=== honest limits ===
  - This is WEIGHT RECONSTRUCTION error, not output quality. A 17% weight error does
    not straightforwardly become a 17% worse model, and nobody should read it that way.
  - 384 rows sampled per tensor, not whole tensors.
  - Attention projections only. No MoE, no embeddings, no lm_head.
  - NO downstream logit or token comparison was run at int4, so the real quality cost
    is unmeasured. This study bounds the WEIGHT error only. Closing that gap needs a
    full end-to-end grid against the reference logits; tools/ref_forward.py has an
    --int8 mode that would be the starting point.
