Token ids alone carry no quality signal, so every id below is decoded back through the
C tokenizer. What the model produced is reproduced verbatim, including the parts that
are not flattering.

--- the full 93-layer, 2.78T-parameter checkpoint ---

  prompt    ids : 1008,10484,318,15383,387
  prompt    txt : The capital of France is
  generated ids : 17374,20829,10,427,414,1008,606,142957
  generated txt :  Paris.",~+            "The Eiffel~
                  (~ marks a newline)

  The first two tokens are 17374 = ' Paris' and 20829 = '.",' - the model answers the
  question CORRECTLY. What follows ('+', indentation, '"The Eiffel') is the base model
  continuing into what looks like a diff or a JSON context. There is no chat template
  and no instruction tuning applied here, so a plain continuation is the expected
  behaviour rather than a defect. See "What it does not do" in the README.

--- an honest caveat about the logit-parity fixture ---

The elementwise logit comparison against the reference (docs/TESTING.md, raw logs in
tests/fixtures/golden/) used prompt ids 3,4,5,6,7, which decode to:

  $%&'(

That is synthetic junk, not text. The agreement it establishes is real and exact, and it
is the strongest correctness evidence in the project - but it is agreement on one
position of a meaningless prompt. It says nothing about output quality, and nothing here
should be read as implying otherwise.
